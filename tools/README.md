# Инструменты

Два работающих инструмента и архив. Сборки фронтенда больше нет:
`src/main/resources/static` — обычные исходники, их правят руками.

## `gen_i18n_fallback.py` — запасной словарь подписей

Обновляет `static/js/i18n-fallback.js`.

**Запускать не обязательно.** Настоящие тексты страница забирает
с сервера синхронным запросом ещё до первой отрисовки (см. начало
`js/i18n-fallback.js`), поэтому подписи на экране приходят из базы.
Словарь в самом файле — страховка на два случая:

1. портал не ответил на запрос текстов — тогда вместо ключей вида
   `sku.column.code` человек увидит русские подписи;
2. ключ есть в коде, а текста в базе ещё нет.

Второго случая быть не должно: ключи добавляются вместе с текстами
в миграции. Так что это гигиена, а не шаг сборки — хорошо запустить
после миграции с текстами, но ничего не сломается, если забыть.

```
python tools/gen_i18n_fallback.py                        # у работающего портала
python tools/gen_i18n_fallback.py --url http://localhost:8080
python tools/gen_i18n_fallback.py --from-json ru.json
python tools/gen_i18n_fallback.py --psql --db tplcp --user postgres
python tools/gen_i18n_fallback.py --dry-run              # только показать
```

По умолчанию тексты берутся **у работающего портала**
(`GET /api/i18n/texts/ru`) — это тот же источник, что база, только без
`psql`, пароля и возни с `PATH`. Вариант с `psql` остался на случай,
когда приложение не запущено, а база под рукой; если `psql` не в `PATH`,
инструмент говорит это словами, а не роняет трейсбек.

Он обновляет русские значения уже перечисленных ключей и добавляет те,
на которые ссылается статика. Второй словарь в файле — перевод по
русскому тексту — **не трогает**: его ключи это русские литералы,
написанные в коде прототипа, они фиксированы, и подменять их новым
текстом из базы нельзя, иначе подпись перестанет находиться.

### Подключение и пароль (Windows 11)

Инструмент не хранит пароль и не спрашивает его: подключение задаётся
**переменными среды libpq**, как у любого инструмента PostgreSQL, а
пароль `psql` читает сам.

| Переменная | Зачем |
|---|---|
| `PGDATABASE` | база, иначе придётся писать `--db tplcp` |
| `PGUSER` | пользователь |
| `PGHOST`, `PGPORT` | если база не на localhost:5432 |
| `PSQL` | полный путь к `psql.exe`, если его нет в `PATH` |
| `PGPASSWORD` | пароль — способ простой, но не лучший, см. ниже |

**Пароль правильнее держать в `pgpass.conf`,** а не в переменной среды:
переменные видны любому процессу пользователя и попадают в отладочные
дампы, а файл лежит в профиле и защищён правами на профиль.

Создайте `%APPDATA%\postgresql\pgpass.conf` (папки `postgresql` может
не быть — создайте) со строкой вида

```
localhost:5432:*:postgres:ВАШ_ПАРОЛЬ
```

Формат: `хост:порт:база:пользователь:пароль`, `*` означает «любая».
Файл в репозиторий не кладём никогда.

`psql` в `PATH` держать не обязательно: инструмент сам ищет его
в `PATH`, в переменной `PSQL` и в обычных местах установки
(`C:\Program Files\PostgreSQL\<версия>\bin`), выбирая самую новую
версию. Если не нашёл — говорит, что делать, и не падает трейсбеком.

На машине разработки сейчас PostgreSQL 18, то есть
`C:\Program Files\PostgreSQL\18\bin`. Установщик PostgreSQL `PATH`
по умолчанию не меняет — это нормальное состояние, а не поломка:
`psql --version` в консоли не сработает, а инструмент работать будет.

Переменные среды, заданные через окно Windows или
`SetEnvironmentVariable`, видит только **новый** процесс. После их
правки закройте и откройте консоль, а PyCharm перезапустите целиком —
иначе он передаст дочернему процессу прежнее окружение. Это самая
частая причина «я же задал, а не работает».

Имена внутри инструмента — латиницей: консоль Windows обычно не в UTF-8,
и кириллица в именах функций превращает трейсбек в кашу ровно тогда,
когда он нужен.

## `one_file.py` — собрать статику в один файл

```
python3 tools/one_file.py src/main/resources/static /tmp/portal.html
python3 tools/one_file.py src/main/resources/static /tmp/portal.html --cmp <файл>
```

Подставляет содержимое каждого подключённого файла на место ссылки —
то есть делает то, что делает браузер при загрузке страницы.

Два применения. Первое: показать вёрстку без сервера или отдать портал
одним файлом. Второе, историческое: сразу после распила собранный файл
совпадал с прежним `index.html` **побайтово**, и это было
доказательством, что распил механический. С ключом `--cmp` инструмент
сам сверяет байты и возвращает код выхода 1 при расхождении.

После того как файлы начали править, совпадения с прежним `index.html`
больше нет и быть не должно — проверка была одноразовым пропуском.

## `attic/` — не запускается, хранится как история

**`patch_demo.py`** — сборщик, которым `index.html` собирался до
распила. Делал две разные вещи: расставлял по разметке демо 348 ключей
переводов, переносил поля между вкладками, привязывал строки карточки
товара к колонкам справочника, переводил надписи внутри кода прототипа
— и приклеивал к файлу наши блоки JS.

Первое было одноразовой работой и теперь заморожено в самой разметке.
Второе заменили обычные `<script src>`.

Запускать его нельзя: он возьмёт исходное демо и соберёт файл без всего,
что сделано после распила. Лежит здесь, чтобы был ответ на вопрос
«откуда в разметке взялся этот ключ и почему поле уехало на другую
вкладку» — в коде проходов это написано.

**`split_index.py`** — сам распил. Один раз сделал своё дело: вырезал
25 блоков в файлы и заменил их ссылками. Второй раз запускать незачем —
резать больше нечего.
