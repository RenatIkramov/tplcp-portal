# 3PL Customer Portal

B2B self-service портал 3PL-оператора. Бэкенд на Spring Boot + PostgreSQL,
фронтенд — согласованный с заказчиком HTML-прототип, подключённый к API.

## Где что лежит

| Путь | Что это |
|---|---|
| `src/main/java/com/ahlers/portal3pl/` | код приложения |
| `src/main/resources/application.yml` | подключение к базе, dev-режим |
| `src/main/resources/static/index.html` | портал (демо, подключённое к API) |
| `src/test/java/com/ahlers/portal3pl/` | тесты |
| `V12…V16*.sql` | миграции базы (накатываются вручную) |
| `requests.http` | примеры всех запросов к API |
| `patch_demo.py` | накладывает подключение к API на исходный демо-файл |

Пакеты приложения:

| Пакет | Назначение |
|---|---|
| `config` | контекст запроса, изоляция данных, текущий пользователь |
| `stock` | запасы и детализация по партиям |
| `documents` | поступления, заказы, перемещения; черновики и отправка в WMS |
| `catalog` | номенклатура, справочники, биллинг |
| `common` | преобразование имён колонок и приведение типов |
| `dev` | служебные эндпоинты, только в dev-режиме |

## Запуск

1. База `tplcp` со схемой `dbo`, миграции накатаны по порядку (см. ниже).
2. JDK 21 или новее: *File → Project Structure → SDK*.
3. *File → Open* → папка с `pom.xml`, дождаться загрузки зависимостей.
4. Открыть `PortalApplication.java`, нажать зелёный треугольник.
5. Открыть `http://localhost:8080/`.

Пароль роли `portal_app` задан в `V12__rls.sql` как `portal_app_dev`
и продублирован в `application.yml` — меняются вместе.

## Миграции

Накатываются вручную (DBeaver, pgAdmin, psql) строго по порядку:

| Файл | Что добавляет |
|---|---|
| `portal_schema_full.sql` | вся схема: таблицы, справочные данные, представления |
| `V12__rls.sql` | роль `portal_app`, политики изоляции данных (RLS) |
| `V13__depositor_resolution.sql` | выбор поклажедателя, проверка прав доступа |
| `V14__dev_helpers.sql` | служебные функции для разработки |
| `V15__stock_lines_extra.sql` | группа товара и брак на экране запасов |
| `V16__document_lifecycle.sql` | жизненный цикл документа: черновики, статусы, аудит |

Демо-данные — `demo_data.sql`, в продакшн не накатываются.

Flyway в `pom.xml` есть, но в `application.yml` выключен: схема заведена
вручную. Чтобы передать её Flyway, нужна пустая база и файлы миграций
в `src/main/resources/db/migration`.

## Проверка

В браузере (dev-режим, поклажедатель указывается параметром):

| Адрес | Что показывает |
|---|---|
| `/api/dev/depositors` | поклажедатели с кодами и UUID |
| `/api/dev/users` | пользователи и роли |
| `/api/stock?depositorCode=D-001` | запасы, 9 строк |
| `/api/receipts?depositorCode=D-001` | поступления |
| `/api/sku?depositorCode=D-001&search=рога` | номенклатура с поиском |

Все запросы, включая запись, собраны в `requests.http`.

Тесты: `ReadApiTest` — чтение и изоляция данных, `DraftTest` — черновики
документов. Запускать зелёным треугольником из открытого файла. Тесты
работают против локальной базы с демо-данными и убирают за собой созданные
документы.

## Три вещи, которые важно понимать в этом коде

**В SQL нет фильтра по поклажедателю.** Его накладывает база политикой RLS.
Сделано специально: один забытый `WHERE` в одном отчёте перестаёт быть
утечкой данных между клиентами оператора (§5 ТЗ).

**`set_config` вызывается внутри транзакции.** Приложение работает через пул
соединений: вне транзакции нет гарантии, что запрос данных уйдёт в то же
соединение. Правило без исключений — контекст выставляет каждый публичный
метод сервиса, полагаться на вызывающего нельзя.

**Подключаемся ролью `portal_app`, а не владельцем схемы.** Владелец обходит
политики RLS, и изоляция молча перестала бы работать.

## Решения, принятые по ходу

Подробности — в документах проекта на claude.ai.

- **Р1.** Одна строка документа может относиться к нескольким партиям.
  Плановое количество хранится один раз (запись без партии), фактическое —
  на записях с партиями; состав документа агрегирует, детализация разворачивает.
- **Р2.** Два юрлица оператора на одном экземпляре портала; изоляции между
  ними нет, различаются реквизиты и контент.
- **Р4.** Регистры и справочники, ведущиеся в WMS, — кэш, а не источник истины.
  У данных показывается время последней синхронизации.
- **Р5.** Документ принадлежит порталу, пока он черновик. После подтверждения
  владелец — WMS: статусы приходят оттуда, портал документ не редактирует.
