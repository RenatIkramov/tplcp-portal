# 3PL Customer Portal

B2B self-service портал 3PL-оператора. Бэкенд на Spring Boot + PostgreSQL,
фронтенд — согласованный с заказчиком HTML-прототип, подключённый к API.

## Где что лежит

| Путь                                  | Что это                                    |
|---------------------------------------|--------------------------------------------|
| `src/main/java/com/ahlers/portal3pl/` | код приложения                             |
| `src/main/resources/application.yml`  | подключение к базе, настройки Flyway       |
| `src/main/resources/db/migration/`    | миграции базы (Flyway), V1…V66             |
| `src/main/resources/static/`          | фронтенд: `index.html`, `css/`, `js/`      |
| `src/test/java/com/ahlers/portal3pl/` | тесты, в том числе браузерные              |
| `requests.http`                       | примеры запросов к API                     |
| `tools/`                              | инструменты и архив, см. `tools/README.md` |

Пакеты приложения:

| Пакет       | Назначение                                                     |
|-------------|----------------------------------------------------------------|
| `config`    | контекст запроса, изоляция данных, текущий пользователь        |
| `auth`      | вход, сессии, роли, выбор поклажедателя, пароли                |
| `admin`     | пользователи, доступы, справочники уровня портала              |
| `stock`     | запасы и детализация по партиям                                |
| `documents` | поступления, заказы, перемещения; черновики и отправка в WMS   |
| `catalog`   | номенклатура, контрагенты, биллинг                             |
| `columns`   | справочник колонок: выбор, порядок, переименование под клиента |
| `i18n`      | языки и тексты интерфейса                                      |
| `excel`     | шаблоны и импорт номенклатуры                                  |
| `common`    | имена колонок, приведение типов, тексты отказов                |

### Фронтенд

Обычные файлы, которые правятся руками. Сборки нет — её выбросили
вместе со сборщиком `patch_demo.py` (лежит в `tools/attic/`).

| Путь                         | Что это                                   |
|------------------------------|-------------------------------------------|
| `static/index.html`          | разметка всех экранов, ~1 500 строк       |
| `static/css/portal.css`      | оформление прототипа                      |
| `static/js/prototype.js`     | собственный код демо                      |
| `static/js/portal/*.js`      | наш код, по файлу на раздел               |
| `static/js/i18n-fallback.js` | `T()`, `TRU()` и запасные русские подписи |

`i18n-fallback.js` собирается из базы инструментом
`tools/gen_i18n_fallback.py` — руками его не правят. Настоящие тексты
страница забирает с сервера до первой отрисовки; словарь в файле —
страховка на случай, когда портал не ответил.

Скрипты подключены **обычными** `<script src>`, не модулями, и это
не случайность: код прототипа держит состояние в лексических
глобальных переменных (`const tableColumnState = …` на верхнем
уровне), а у ES-модулей своя область видимости — переход на них
сломал бы разом 635 обращений и 310 `onclick=` в разметке.

**Порядок подключения в `index.html` важен и менять его нельзя.** Файлы
из `js/portal/` переопределяют глобальные функции прототипа, и побеждает
последнее присваивание: `card.js` перекрывает `portalOpenDocument`
из `docs.js`, `draft.js` — его же поверх `card.js`.

## Запуск

1. PostgreSQL 16 или новее, база `tplcp`, в ней схема `dbo`.
2. JDK 21 или новее: *File → Project Structure → SDK*.
3. *File → Open* → папка с `pom.xml`, дождаться загрузки зависимостей.
4. Открыть `PortalApplication.java`, нажать зелёный треугольник.
5. Открыть `http://localhost:8080/`.

Миграции накатывает **Flyway при старте приложения** — руками ничего
накатывать не нужно. Подключается он владельцем схемы, приложение
работает ролью `portal_app`; и пользователи, и пароли заданы
в `application.yml`.

Пароль роли `portal_app` задан в `V12__rls.sql` и продублирован
в `application.yml` — меняются вместе.

**На чистой базе** портал откроется пустым: ни пользователей, ни
товаров. Демо-данные — `tools/dev-data.sql`, накатить один раз вручную,
см. `tools/README.md`. Это не миграция нарочно: такие данные нужны
только на машине разработчика.

**`baseline-version: 20`** в настройках Flyway — след истории: схема
до V20 накатывалась вручную, и на базах, заведённых тогда, Flyway
считает первые двадцать версий уже применёнными. На чистой базе
применяются все, с V1.

## Проверки

```
mvn clean test                          все, 223 проверки
mvn test -DexcludedGroups=browser       без браузерных
```

Проверки работают против **локальной базы** и убирают за собой
созданные строки. Из 223 двадцать — браузерные: Spring поднимает портал
на свободном порту, Playwright открывает его настоящим Chromium
и смотрит, что отрисовалось и что ушло на сервер. Первый запуск
скачивает Chromium (~130 МБ); без сети браузерные помечаются
пропущенными, а не падают — см. `BrowserTestBase`.

Подробности — документ «Браузерные проверки» в проекте на claude.ai.

## Четыре вещи, которые важно понимать в этом коде

**В SQL нет фильтра по поклажедателю.** Его накладывает база политикой
RLS. Сделано специально: один забытый `WHERE` в одном отчёте перестаёт
быть утечкой данных между клиентами оператора (§5 ТЗ).

**Подключаемся ролью `portal_app`, а не владельцем схемы.** Владелец
обходит политики RLS, и изоляция молча перестала бы работать. Отсюда
же правило проверки: SQL, проверенный под `postgres`, не проверен
вовсе — под ним политики не участвуют, а `DELETE` без выставленного
контекста удаляет ноль строк **без ошибки**.

**`set_config` вызывается внутри транзакции.** Приложение работает
через пул соединений: вне транзакции нет гарантии, что запрос уйдёт
в то же соединение. Правило без исключений — контекст выставляет каждый
публичный метод сервиса, полагаться на вызывающего нельзя. Практически
это значит: первая строка любого нового метода чтения —
`depositorScope.apply()`.

**Применённую миграцию не правят никогда.** Flyway держит контрольную
сумму, и правка накатанного файла ломает проверку у всех, кто базу
уже обновил. Любое дополнение — новая версия. Следствие, которое
смущает при первом чтении: анализатор IDE показывает в старых миграциях
«не найдена колонка». Так и должно быть — миграция описывает схему
своего дня, а не сегодняшнюю.

## Решения, принятые по ходу

Подробности — в документах проекта на claude.ai.

- **Р1.** Одна строка документа может относиться к нескольким партиям.
  Плановое количество хранится один раз (запись без партии), фактическое —
  на записях с партиями; состав документа агрегирует, детализация
  разворачивает.
- **Р2.** ~~Два юрлица оператора на одном экземпляре портала~~ —
  **отменено заказчиком.** Счета и акты приходят через интеграцию
  готовыми, значит реквизиты юрлица порталу не нужны. Схема под Р2
  создана и остаётся неиспользованной.
- **Р3.** React не будет, сборщика фронтенда нет — см. выше.
- **Р4.** Регистры и справочники, ведущиеся в WMS, — кэш, а не источник
  истины. Превышение доступного количества предупреждает, но не
  запрещает: последнее слово за WMS.
- **Р5.** Документ принадлежит порталу, пока он черновик. После
  подтверждения владелец — WMS: статусы приходят оттуда, портал документ
  не редактирует.
- **Р6.** Номер документа — `[тип][YYMMDD][счётчик]`, например
  `O261014001`. Счётчик на тип и день, один на всех поклажедателей.
- **Р7.** Документ появляется в базе по кнопке «Сохранить», а не при
  открытии карточки.
